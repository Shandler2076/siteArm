# Analyse de sécurité du site — 19 novembre 2026

Analyse en profondeur du code (lecture seule), faite à la demande du mainteneur. Rien n'a été
modifié par l'analyse. Les corrections proposées attendent son accord (« lance tout »).

## Élevé

1. **Un bureau de paroisse peut prendre le compte d'un Trésorier (y compris national).**
   Le Chef ou le Secrétaire d'une paroisse peut réinitialiser le mot de passe d'un membre de sa
   paroisse. Les trésoriers (paroisse, circuit, région, et même le Trésorier national) n'ont pas le
   « droit de gérer » : le refus ne les protège donc pas. Le nouveau mot de passe donne alors les
   pouvoirs de trésorerie nationale (préparer les reversements, voir les quittances), sans double
   vérification.
   - Correction proposée : refuser la réinitialisation par un bureau local pour tout membre qui a
     un mandat en cours (seul le BN la fait) ; étendre la double vérification aux trésoriers
     nationaux et aux validateurs des reversements.
2. **Le paiement simulé pourrait être allumé sur le vrai site** (mauvaise configuration) : chacun
   pourrait alors « payer » sans argent et recevoir de vraies quittances.
   - Correction proposée : le site refuse de démarrer si le paiement simulé est actif hors site
     d'essai ; le script d'installation ne met plus « site d'essai » par défaut ; mention « SIMULÉ »
     sur les quittances de démonstration.

## Moyen

3. **Double vérification et changement de mot de passe** : la page de changement du mot de passe
   et l'activation de la double vérification sont accessibles avant le code à 6 chiffres. Avec le
   seul mot de passe, quelqu'un pourrait activer SA propre application sur un compte BN pas encore
   protégé, ou changer le mot de passe d'un compte protégé.
   - Correction proposée : changement libre du mot de passe seulement à la première connexion ;
     sinon, code à 6 chiffres exigé ; avertir le titulaire à chaque activation.
4. **Blocage des connexions seulement par identifiant** : les matricules se devinent ; un
   attaquant peut essayer 1 ou 2 mots de passe sur chaque compte, ou bloquer le compte du
   Président en continu.
   - Correction proposée : limite aussi par adresse IP (en tenant compte du relais d'alwaysdata).
5. **« Payer pour un autre membre »** : en essayant des matricules, un membre peut connaître le
   nom, la paroisse… et voir qu'un autre membre a une **amende** (donc une sanction).
   - Correction proposée : ne jamais afficher les amendes d'un tiers ; inscrire chaque recherche
     au journal ; limiter le nombre de recherches. Même chose pour l'aperçu des mutations.
6. **Envois de fichiers** : la taille est vérifiée après réception complète ; Pillow lit tous les
   formats d'image avant le contrôle.
   - Correction proposée : refuser tôt les envois trop gros ; n'ouvrir que JPEG et PNG.
7. **Versions des bibliothèques non figées** (`>=`) : une mise à jour peut installer une version
   différente de celle testée.
   - Correction proposée : figer les versions exactes ; ajouter `defusedxml` ; contrôle
     `pip-audit` dans les tests automatiques.

## Faible

- Fichier Excel « bombe » (lots, BN seulement) : limiter la taille décompressée et les lignes.
- Page publique de l'autorisation : masquer la photo après la fin de validité ; ne pas indexer.
- Journal : les anciens et nouveaux numéros de téléphone / e-mails y restent pour toujours
  (contraire à la conservation limitée APDP) : n'y garder que le nom des champs modifiés.
- Clés de double vérification stockées en clair dans la base (et les sauvegardes) : les chiffrer.
- Sauvegarde : mot de passe de la base visible dans la liste des processus ; pas de rotation.
- Administration technique (`/gestion/`) : peut modifier statut, catégorie, mandats sans passer
  par les règles du site ni le journal : la mettre en lecture seule ou la fermer en production.
- En-têtes de sécurité : ajouter CSP et Permissions-Policy.
- Courriers importés en PDF : les servir en téléchargement (un PDF peut contenir du code).
- Clé secrète de secours en mode développement : la réserver aux tests.

## Vérifié et correct

Clé secrète obligatoire en production, cookies sécurisés, HTTPS forcé (HSTS), protection contre
l'affichage dans un cadre ; double vérification solide (codes non rejouables, blocage après
5 erreurs) ; fichiers privés jamais publics (photos, CIP, signatures) ; pas d'accès aux données d'un
autre par changement de numéro dans l'adresse ; exports Excel sans formules ; pas de faille XSS
trouvée ; liens de vérification (QR) impossibles à deviner ; paiements confirmés une seule fois,
montants recalculés par le site ; `.env`, base et fichiers privés hors de GitHub ; commandes de
démonstration bloquées hors site d'essai ; sauvegardes chiffrées (AES-256).
